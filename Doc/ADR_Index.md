## ADR-001

**フロントエンドは純粋なUI（選択的適用）**

- **日付**: 2026-02-11
- **ステータス**: 承認済
- **最終更新**: 2026-04-07
- **関連**: Doc/architecture.md §2.2

### 背景

オープンソース + セルフホスト前提のSPAにおいて、APIキーなどの
秘密情報をクライアント側に持たせるわけにはいかない。一方で、
モデルの意味解析やテーブル生成をすべて外部サービス（LLM等）に
委譲すると、AIがないと何もできないシステムになってしまう。
どこまでをフロントエンドに持たせ、どこから外に出すかの線引きが
必要。

**主な判断要因:**

- Volatile Canvas思想（レビューは一時的なもの、セッションに閉じる）
- セキュリティ（フロントエンドに秘密情報を置かない）
- 堅牢性・レスポンス（AIがダウンしていても図＋表の表示は成立すべき）
- オープンソース + セルフホスト可能性

### 決定

**要約:** フロントエンドは表示と接続に専念し、秘密情報を持たない。ただし意味解析と表生成はフロントエンドで行う。

SPAは「表示と接続」だけを担当することを基本方針とし、秘密情報
（APIキー等）は一切持たないことにした。ただしモデルの意味解析
（PlantUMLサブセットのパース）と状態遷移表の生成については、
LLM不要の確定的処理であり、フロントエンドで完結させる方が
堅牢性とレスポンスの面で優れるため、例外としてフロントエンドで
実行する。

### 検討したが採用しなかった選択肢

- **すべての処理を外部サービスに委譲する純粋なUI** — AIがダウンすると図＋表の表示すら成立しなくなり、堅牢性が著しく低下する
- **意味解析もAIに任せる（LLMでPlantUMLを解釈）** — 文法的に確定的な処理をLLMに投げるのは過剰であり、レスポンスと信頼性が下がる

### 結果・影響

**メリット:**

- AIがなくても図＋表の表示が成立する
- APIキー管理はn8n側に集約され、フロントエンドの攻撃面が減る
- 意味解析は純粋関数となり、ユニットテストが容易

**受け入れる負債・制約:**

- フロントエンドにパーサーとテーブル生成器を持つ必要があり、バンドルサイズに影響する

**リスク:**

- PlantUMLサブセットを拡張するたび、パーサーを更新するコストが発生する

## ADR-002

**n8nをオーケストレーターとして導入する**

- **日付**: 2026-02-11
- **ステータス**: 承認済
- **最終更新**: 2026-04-07
- **関連**: Doc/architecture.md §7

### 背景

AIチャット（Gemini API）や将来的な外部サービス連携（Slack,
GitHub等）において、APIキー管理とワークフロー処理をどこで行うかが
設計上の論点だった。フロントエンドには秘密情報を置かない方針
（ADR-001）があるため、何らかの中継層が必要。

**主な判断要因:**

- APIキー管理の一元化
- フロントエンド側での秘密情報排除
- 将来の外部連携拡張性
- セルフホスト可能であること

### 決定

**要約:** n8nをオーケストレーターとして採用し、AI中継・APIキー管理・外部サービス連携をすべて担わせる。

n8nをDocker Composeで起動する前提のオーケストレーターとして採用
することにした。AIチャット（Gemini API）の中継、APIキーの保管、
将来のSlack/Teams/Discord/GitHub連携などをすべてn8nのワークフローで
扱う。n8nはオープンソースかつセルフホスト可能で、ノーコードで
ワークフローを組めるため、拡張時のコストも低い。

### 検討したが採用しなかった選択肢

- **自前のバックエンドサーバーを立てる** — SPA + 静的ホスティングの方針が崩れ、運用の複雑さが増す
- **Gemini APIを直接フロントエンドから呼ぶ** — APIキーがクライアントに露出し、ADR-001に反する

### 結果・影響

**メリット:**

- APIキーがフロントエンドから完全に分離される
- ワークフロー追加だけで外部連携を増やせる
- n8n UIでプロンプトエンジニアリングが完結する

**受け入れる負債・制約:**

- Docker環境が必須になる（ただしPlantUML Serverと同様なので追加コストは小さい）
- n8nのライセンス（Sustainable Use License / fair-code）に依存する

**リスク:**

- n8nのワークフローJSONをリポジトリに同梱するが、n8nのバージョン差で互換性問題が起きる可能性

## ADR-003

**意味解析とテーブル生成はフロントエンドのパーサーとアルゴリズムで行う**

- **日付**: 2026-04-05
- **ステータス**: 承認済
- **最終更新**: 2026-04-07
- **関連**: Doc/architecture.md §6.1, NeoCEGプロジェクト

### 背景

PlantUMLソースから状態遷移表などを生成する処理を、どこで行うか。
以前の設計ではテーブル生成をLLM（n8n経由）に委譲する方針だったが、
LLM依存が強くなり、AIが落ちると図も表も見られなくなる問題があった。

**主な判断要因:**

- AIなしでも図＋表の表示が成立する堅牢性
- 確定的な処理でLLMを使わないことによる高速性と安定性
- NeoCEGでの実績（テキスト→正規モデル→図＋表のパターン）
- パーサーのテスト容易性

### 決定

**要約:** PlantUMLサブセットのパーサーをフロントエンドに持ち、StateMachineModelを自前で構築する。テーブル生成も純粋アルゴリズムで実行する。

意味解析（PlantUMLソース→StateMachineModel）とテーブル生成
（StateMachineModel→状態遷移マトリクス）をすべてフロントエンドの
純粋関数として実装することにした。PlantUMLの状態遷移図サブセットは
文法が限定的であり、パーサーの実装コストは低い。LLM依存を排除する
ことで、AIがなくても図＋表の表示が成立する。NeoCEGで確立した
「テキスト→正規モデル→図＋表」パターンを踏襲している。

### 検討したが採用しなかった選択肢

- **テーブル生成をLLM（n8n経由）に委譲する（旧方針）** — AI依存が強くなり、AIダウン時に図＋表すら表示できなくなる
- **パーサーをバックエンドに置く** — SPA + 静的ホスティングの方針に反し、バックエンドの運用コストが発生する

### 結果・影響

**メリット:**

- AIなしでも図＋表の表示が完結する
- パーサーは純粋関数なのでゴールデンテストが書きやすい
- 解析結果が確定的で、同じソースから常に同じ表が得られる

**受け入れる負債・制約:**

- サブセット拡張のたびにパーサーを更新する必要がある
- フロントエンドのバンドルにパーサーが含まれる

**リスク:**

- 他の図種（アクティビティ図等）に拡張する際、パーサーごとに実装が必要になる

## ADR-004

**EBNF文法は静的ファイルとして定義する**

- **日付**: 2026-02-11
- **ステータス**: 承認済
- **最終更新**: 2026-04-07
- **関連**: Doc/architecture.md

### 背景

PlantUMLサブセットの文法をユーザーや開発者が参照できるように
表示する必要がある。定義の格納場所として、静的ファイルに
持つか、LLMに都度生成させるかの選択肢があった。

**主な判断要因:**

- 文法定義の信頼性・一貫性
- 文法定義の変更頻度の低さ
- LLM出力のばらつきによる不安定さ

### 決定

**要約:** EBNF文法はフロントエンドに静的ファイルとして持つ。

PlantUMLサブセットのEBNF文法定義はフロントエンドに静的ファイル
として格納することにした。文法は変更頻度が低く、定義の一貫性が
信頼できる必要があるため、LLMに都度生成させるのは不安定で
不適切。静的定義が最も信頼性が高い。

### 検討したが採用しなかった選択肢

- **EBNF文法をLLMに都度生成させる** — LLM出力のばらつきで定義が揺れ、信頼性が損なわれる
- **EBNF文法を外部APIから取得する** — オフラインで表示できなくなり、セルフホスト方針に反する

### 結果・影響

**メリット:**

- 文法定義が常に一貫している
- オフラインでも表示できる
- AIに依存しない

**受け入れる負債・制約:**

- 文法を変更するたびに静的ファイルを更新する必要がある

## ADR-005

**AIレスポンスの解析はn8nワークフロー内で行う**

- **日付**: 2026-02-11
- **ステータス**: 承認済
- **最終更新**: 2026-04-07
- **関連**: Doc/architecture.md §7.2

### 背景

AIチャット（Gemini）のレスポンスにはPlantUMLコードブロックが
含まれることがあり、そこからソースコードを抽出してユーザーに
「適用」ボタンを提示する必要がある。この抽出処理をどこで
行うかが論点だった。

**主な判断要因:**

- フロントエンドを純粋なUIに保つ方針（ADR-001）
- プロンプトエンジニアリングの一元化
- AIレスポンス形式の変更に対する柔軟性

### 決定

**要約:** LLMレスポンスからのPlantUMLコードブロック抽出はn8nワークフロー内で実行する。

AIレスポンスのパース（```plantuml ブロックの抽出など）は
n8nワークフロー側で行い、フロントエンドには構造化済みJSON
（text と suggestedSource のフィールドを持つ）として返すことに
した。フロントエンドは受け取ったJSONを表示するだけで済み、
レスポンス形式が変わってもn8n側の修正で対応できる。

### 検討したが採用しなかった選択肢

- **フロントエンドでAIレスポンスをパースする** — レスポンス形式の変更時にフロントエンドを修正する必要があり、UIロジックが重くなる
- **AIに最初から構造化JSONで返させる（function calling等）** — Geminiの機能と依存してしまい、他のLLMへの差し替えが難しくなる

### 結果・影響

**メリット:**

- フロントエンドはUI表示に専念できる
- レスポンス整形がn8nで一元管理される
- LLMの差し替え時にn8n側のみを更新すれば済む

**受け入れる負債・制約:**

- n8nワークフローに解析ロジックが埋まる

**リスク:**

- n8nワークフローが複雑化する可能性

## ADR-006

**PlantUML SVGを直接表示し、ネイティブSVGオーバーレイにマーカーを描く**

- **日付**: 2026-04-07
- **ステータス**: 承認済
- **最終更新**: 2026-04-07
- **関連**: Doc/architecture.md §ADR-006, Doc/adr/ADR-007-markers-without-element-binding.yaml

### 背景

モデル図のレビューで「ここに注目」を示すためのUIをどう実装するか。
当初はReact FlowでPlantUMLの内容を描き直す方針だったが、
エッジルーティングとラベル配置がPlantUMLと一致せず、図の品質が
著しく低下することが実装で確認された。次にExcalidrawを
ホワイトボードとして使う案を試したが、機能が過剰でマーカーUIの
実装に遠回りが必要であり、IDがランダム置換される・削除が
正しく効かないなどの問題があった。

**主な判断要因:**

- 図の品質（PlantUMLのレンダリングそのままを維持したい）
- マーカーUIの実装のシンプルさ
- バンドルサイズの抑制
- 将来のリアルタイム協調編集への拡張パス

### 決定

**要約:** PlantUML Serverが生成したSVGをそのまま表示し、その上にネイティブSVGのオーバーレイ層を重ねてマーカーを描く。React FlowもExcalidrawも使用しない。

PlantUML Serverから取得したSVGを<img>または<svg>で直接表示し、
その上にネイティブSVGのオーバーレイ層を重ねて、レビューアが
マーカー（楕円・矩形・矢印）を描けるようにした。React Flowや
Excalidrawなどの外部ホワイトボードフレームワークは一切使わず、
200行程度の自前SVG実装で完結する。必要なのは「ここに注目を
示せるマーカー」だけなので、シンプルな自前実装が最適。

### 検討したが採用しなかった選択肢

- **React FlowでPlantUMLを描き直す** — エッジルーティングとラベル配置がPlantUMLと一致せず、図の品質が低下することを実装で確認
- **Excalidrawをホワイトボードとして使う** — 機能が過剰で、マーカーUIの実装に遠回りが必要。IDがランダム置換される等の固有の問題があり、1.8MBのバンドル追加に見合わない
- **Canvas APIで自前実装** — SVGのパン/ズーム/座標変換が自然にできるので、Canvasを使う利点がない

### 結果・影響

**メリット:**

- PlantUMLのレンダリング品質をそのまま維持できる
- バンドルサイズが大幅に削減された（1.6MB → 600kB）
- 見た目とイベント挙動を完全にコントロールできる
- 将来のリアルタイム協調編集は、マーカー差分をWebSocket送信するだけで実装可能

**受け入れる負債・制約:**

- マーカーUIのすべて（選択・移動・リサイズ・削除など）を自前実装する必要がある

**リスク:**

- 将来より高度なホワイトボード機能が必要になった場合、自前実装の限界に達する可能性

## ADR-007

**マーカーはモデル要素に紐づけず、AIに解釈させる**

- **日付**: 2026-04-07
- **ステータス**: 承認済
- **最終更新**: 2026-04-07
- **関連**: Doc/architecture.md §ADR-007, Doc/adr/ADR-006-native-svg-overlay-for-markers.yaml

### 背景

レビューで「ここに注目」を示すマーカーを、特定のモデル要素
（Idle状態、特定の遷移など）に厳密に紐づけるべきかが論点
だった。以前の設計ではマーカーをクリック座標からモデル要素
IDに紐づける案を試したが、人間は一発で正確にクリックできない
ことが多く、厳密照合は失敗時のリカバリーが面倒という問題が
あった。

**主な判断要因:**

- 人間の自然なレビュー所作（「だいたいこのあたり」）
- 他のモデル図種への汎用性
- 実装のシンプルさ
- AIの曖昧性処理能力

### 決定

**要約:** マーカーは特定のモデル要素IDに紐づけない。座標と色のみを持ち、AIがコンテキストからどの要素を指しているか解釈する。

マーカーは特定のモデル要素IDに紐づけないことにした。
MarkerStoreはマーカーの座標と色だけを保持し、AIチャットの
コンテキストとして「マーカー一覧」と「モデル要素の座標」の
両方をAIに渡す。AIは必要に応じて「赤の楕円はIdle状態を
指していますね」と解釈し、曖昧なら人間に質問する。

### 検討したが採用しなかった選択肢

- **マーカーをクリック座標から最も近いモデル要素に厳密に紐づける** — 人間は一発で正確にクリックできないことが多く、失敗時のリカバリーが煩雑
- **マーカーごとに『対象要素』ドロップダウンで明示選択させる** — レビュー中の操作が重くなり、『だいたいこのあたり』という自然な所作と合わない

### 結果・影響

**メリット:**

- 人間の自然な「だいたいこのあたり」というレビュー所作と合致する
- 状態遷移図以外のモデル図（アクティビティ図、要求系統図等）でも同じ仕組みが使える
- マーカー実装側の責任が減り、シンプルで堅牢になる
- AIは元々曖昧性に強く、座標情報からの推論に向いている

**受け入れる負債・制約:**

- マーカーとモデル要素の対応が常に一意に決まるわけではない

**リスク:**

- AIの解釈が的外れだった場合、ユーザーが意図した要素と違う要素について議論が進む可能性

## ADR-008

**ModelLogueのスコープ境界——前後の業務ワークフローはn8n側に委ねる**

- **日付**: 2026-04-08
- **ステータス**: 承認済
- **最終更新**: 2026-04-08
- **関連**: Doc/requirements/user_requirements.yaml, Doc/adr/ADR-002-n8n-as-orchestrator.yaml

### 背景

モデルレビューは開発業務の中の一工程であり、前段（初版モデルの
生成）と後段（合意形成・保留・仕様不備のフィードバック）を伴う。
この前後の業務プロセスは現場ごとに異なる。ModelLogue本体が
どこまでの範囲を担い、どこから先を外部（運用ワークフロー）に
委ねるかが曖昧だと、要求が際限なく膨らんでスコープが破綻する。

特に、ユーザー要求の段階では「初版を依頼する」「セッションを
終了する」といったタスクが当然存在するが、これらをModelLogue
本体の機能として実装するかどうかは別問題である。

**主な判断要因:**

- システム要求のスコープを有限に保ちたい
- 業務プロセスの現場差異に対応する柔軟性
- n8nオーケストレーター方針（ADR-002）との整合
- ユーザー要求は広く取り、システム要求で実装範囲を絞るという仕様駆動開発の流儀

### 決定

**要約:** ModelLogueの実装範囲はAntigravity図でいう ReviewLoop の内側に専念し、その前後（初版生成、終了後フィードバック）はn8nワークフロー側に委ねる。

モデルレビューの全体プロセスを表す状態遷移図のうち、ModelLogue
本体が機能として実装する範囲は ReviewLoop の内側に限定する
ことにした。ReviewLoop の前段（初版モデルの生成：AI自動生成や
人間による手動記述）と、後段（合意形成・保留・仕様不備の
通知やフィードバック）は、n8nワークフローと現場の運用で
組み立てる範囲とする。

ユーザー要求（UR）レベルでは、レビュー前後のタスクも要求として
広く拾う（例：UR「初版モデル生成を依頼する」「レビューセッション
を終了する」）。しかしシステム要求（SR）レベルでは、ModelLogue
本体が実装するのは「既存のPlantUMLソースを受け取れる」「セッション
成果物をエクスポートできる」という入出力の境界に絞る。具体的な
生成手段や送信先は現場ごとにn8nで構成する。

このスコープ境界は明示的な設計判断であり、将来「なぜ初版生成
機能がないのか」「なぜ終了時に上流工程に通知する機能がないのか」
という疑問が出たときに、本ADRを参照すれば設計意図が伝わるように
記録しておく。

### 検討したが採用しなかった選択肢

- **初版生成機能（要求仕様書からPlantUMLを生成する等）をModelLogue本体に実装する** — 現場ごとに生成方式が異なり、汎用化するとシステムが肥大化する。n8nワークフローで個別構成する方が柔軟
- **レビュー終了時のフィードバック送信先（チケット管理ツール、Slack等）をModelLogue本体に実装する** — 現場ごとに送信先が異なる。n8nワークフローでアダプトする方が柔軟
- **ユーザー要求から前後タスクを排除し、ModelLogueの直接機能だけをURとして書く** — ニーズの全体像を捉えられず、本当の利用文脈が見えなくなる。仕様駆動開発の原則に反する

### 結果・影響

**メリット:**

- システム要求のスコープが明確になり、実装範囲が爆発しない
- 現場ごとの業務プロセス差異にn8nワークフローで対応できる
- ユーザー要求の全体像は失われない（広く拾う）
- ModelLogue本体は再利用しやすい部品として位置づけられる

**受け入れる負債・制約:**

- ModelLogueをそのまま現場で使うには、別途n8nワークフローの構築が必要
- 「これはModelLogueの機能ではない」という説明を都度行う必要がある

**リスク:**

- 境界の判定が将来曖昧になり、UR/SRの対応関係がぶれる可能性

## ADR-009

**複合状態は1階層限定の最小サブセットでサポートする**

- **日付**: 2026-04-08
- **ステータス**: 承認済
- **最終更新**: 2026-04-08
- **関連**: Doc/requirements/system_requirements.yaml SR-002, Doc/architecture.md §6.1, Doc/adr/ADR-010-external-services-for-heavy-or-domain-specific-work.yaml, 業界調査結果：David Harel Statecharts, ISO/IEC/IEEE 29119-4, MATLAB Stateflow, IBM Rhapsody, Yakindu, 秋山浩一氏の状態遷移マトリクス

### 背景

Antigravity氏が作成したModelLogue自身のレビュープロセスを表す
状態遷移図が、フラットな状態遷移図サブセットでは表現しにくい
ことが分かった。具体的には、複数の状態に対する共通遷移
（例：レビューループ全体からの脱出）をフラットに展開すると
遷移が冗長になり、図の意図（フェーズの抽象化）も失われる。

一方で、業界調査の結果、複合状態を完全にサポートしようとすると
実装が大きくなる：
- 直交領域（並行状態）
- ヒストリ擬似状態
- ドット記法による直接進入
- 入れ子の入れ子（多階層ネスト）
- entry/exit point擬似状態
などを全て扱う必要が出てくる。

一方、フラットなままでは、設計のDRY原則も状態遷移表のレイヤード
戦略も活かせない。妥協点が必要だった。

**主な判断要因:**

- 設計のDRY化（共通遷移を親に1回書けば済む）
- 状態遷移表のレイヤード戦略（業界調査結果より、テスト数削減の恩恵）
- 実装コストの抑制（パーサー全面書き直しを避ける）
- PlantUMLサブセットを最初から厳密に絞る方針（ModelLogueは完全なPlantUMLを目指していない）
- 他のモデル図種への将来拡張時にも同じ枠組みを流用できること

### 決定

**要約:** 複合状態は1階層の入れ子に限定してサポートする。直交領域、ヒストリ、ドット記法、多階層ネスト、entry/exit pointは構文エラーとして拒否する。

PlantUMLサブセットに複合状態を導入することにした。ただし、
以下の最小サブセットに限定する：

**サポートする機能**:
- `state X { ... }` による1階層の入れ子
- 複合状態を source とする遷移（グループ脱出：内部のどの状態からでも発火）
- 複合状態を target とする遷移（内部の初期状態へ進入）
- 複合状態の内部の `[*] --> ChildState`（内部初期遷移の定義）
- 状態遷移表のハイブリッドパターン表示（複合状態の行と子状態の行を並べる、子状態はインデント）

**サポートしない機能**（構文エラーで拒否）:
- 入れ子の入れ子（`state X { state Y { ... } }`）
- 直交領域（`--` による並行区分）
- ヒストリ擬似状態（`[H]`、`[H*]`）
- ドット記法による直接進入（`X.Y`）
- entry/exit point擬似状態

この制限により、得たい利点は得つつ、実装コストを抑制できる：
- 設計のDRY化
- レイヤード戦略によるテスト数削減（将来のNスイッチカバレッジ生成サービスとの接続時。生成自体はModelLogue本体の外側で別サービスとして実装する。詳細は ADR-010 参照）
- パーサーは行ベースのまま維持し、中括弧の深さカウンタと
  「現在の親ID」変数を追加するだけで対応可能（30〜50行程度）

1階層の制限自体が意図的な設計判断である。将来「なぜネストできない
のか」と問われたときに、この決定を参照できる。

### 検討したが採用しなかった選択肢

- **複合状態を完全にサポートする（直交領域・ヒストリ・多階層・ドット記法すべて）** — パーサー全面書き直しが必要で実装コストが大きい。ModelLogueはPlantUML完全互換を目指していないのでオーバースペック
- **複合状態をサポートしない（フラットなまま）** — 設計のDRY化とテスト数削減という主要な利点が得られない。Antigravity図のような実用的な状態遷移図を表現できない
- **複合状態をパーサーで扱わず、コメント注釈やラベル命名規則で擬似的に表現する** — 標準的なPlantUML文法から逸脱する非慣用的な書き方になり、可読性とツール互換性が落ちる
- **1階層ではなく2階層まで許す** — 実装コストが急増し（スコープ管理、ID解決の複雑化）、得られる表現力の追加メリットが少ない。必要になった時点で再検討する

### 結果・影響

**メリット:**

- 設計のDRY化が実現される（共通遷移を親に集約できる）
- 状態遷移表でハイブリッドパターン（業界標準）を採用できる
- 将来のNスイッチカバレッジ生成サービス（ADR-010に基づく外部サービス）でレイヤード戦略を適用できる
- パーサー実装コストが抑制される（全面書き直し不要）
- Antigravity図のような実用的な状態遷移図を自然に表現できる
- アクティビティ図など他のモデル図種に拡張する際も同じ枠組みを使える

**受け入れる負債・制約:**

- 深い階層を持つ複雑な状態マシンは表現できない
- 並行状態（直交領域）を含むモデルは扱えない
- ヒストリを使った復元動作は表現できない
- 「PlantUMLそのもの」と思って使うユーザーは構文エラーで戸惑う可能性がある

**リスク:**

- 将来、より高度な表現力が必要になった場合、本ADRを再検討する必要がある
- サポート/非サポートの境界をユーザーに正確に伝える文書化が必要

## ADR-010

**重い処理や領域固有の生成処理は外部サービスとして同一リポジトリ内に分離する**

- **日付**: 2026-04-08
- **ステータス**: 承認済
- **最終更新**: 2026-04-08
- **関連**: Doc/adr/ADR-001-frontend-is-pure-ui.yaml, Doc/adr/ADR-002-n8n-as-orchestrator.yaml, Doc/adr/ADR-009-composite-states-minimal-subset.yaml, Doc/adr/ADR-011-strict-formats-and-deterministic-conversion.yaml

### 背景

ModelLogueはレビュー支援を主目的とするフロントエンドであり、
そこに「重い処理」「領域固有の生成処理」を全て詰め込むと、
バンドルサイズが膨らみ、責務が混ざり、フロントエンドとしての
軽さと再利用性が損なわれる。

一方で、こうした処理（Nスイッチカバレッジ生成、状態遷移表
CSV変換、将来のアクティビティ図のパスカバレッジ等）は、CI/CD
パイプラインから直接呼びたいケースも多く、ModelLogueと結合
していると逆に使いにくい。

既にPlantUML Server（レンダリング）とn8n（オーケストレーション）
が同じパターン（外部サービスとして独立、APIで呼び出す）で
動いている。これを補助的な生成処理にも一貫して適用すべき。

**主な判断要因:**

- ModelLogueフロントエンドの軽量さと責務の明確さの維持
- CI/CDパイプラインからも独立して呼び出せる必要性
- PlantUML Serverやn8nと同じ運用パターンの一貫性
- 領域固有の処理は単独でテスト・進化させたい
- プロジェクト管理のしやすさ（同一リポジトリで全体を把握）

### 決定

**要約:** 重い処理や領域固有の生成処理は、ModelLogueと同じリポジトリ内に独立した補助サービスとして配置する。各サービスはCLI＋APIを持ち、ModelLogueからもCI/CDからも同じインターフェイスで呼び出せる。

Nスイッチカバレッジ生成、状態遷移表CSV変換などの「重い処理」
「領域固有の生成処理」は、ModelLogueフロントエンドに組み込まず、
独立した補助サービスとして提供することにした。

**配置**:
- ModelLogueと同じリポジトリ内（モノレポ的に整理）
- 各サービスは独立したディレクトリ／パッケージとして配置
- 各サービスは独立してデプロイ可能（Dockerコンテナ等）

**インターフェイス**:
- 各サービスはCLIとして単独で実行可能
- 各サービスはAPIサーバーとしても起動可能（PlantUML Serverと同じパターン）
- ModelLogueフロントエンドからは PlantUML Server同様に HTTP で呼び出す
- CI/CDパイプラインからは CLI で直接呼び出すか、APIサーバーに POST する

**第1号サービス**: Nスイッチカバレッジ生成
**第2号候補**: 状態遷移表CSV ↔ PlantUMLソース変換

将来、他のモデル図種（アクティビティ図、要求系統図、クラシフィ
ケーションツリー）に拡張する際も、それぞれ専用の補助サービスを
同じパターンで追加する。

### 検討したが採用しなかった選択肢

- **Nスイッチ生成等をModelLogueフロントエンドに組み込む** — バンドルサイズが膨らみ、CI/CDから単独で呼べず、責務が混ざる。ModelLogueの軽量性が失われる
- **別リポジトリとして完全に独立させる** — プロジェクト全体の把握が困難になり、ModelLogueと補助サービスが共有する型定義やサンプルの管理コストが増える
- **n8nワークフロー内に処理ロジックを書く** — n8nはオーケストレーション層であり、ロジックを埋め込むとテストとバージョン管理が困難になる。n8nワークフローはあくまで配線役に留めるべき

### 結果・影響

**メリット:**

- ModelLogueフロントエンドが軽量に保たれる
- CI/CDから補助サービスを直接呼び出せる
- PlantUML Server / n8n と同じ運用パターンで一貫性がある
- 領域固有の処理を独立してテスト・進化させられる
- 同一リポジトリ内なので型定義やサンプルを共有しやすい
- 将来のモデル図種拡張時も同じパターンで追加できる

**受け入れる負債・制約:**

- サービスごとにCLI + APIサーバーの実装が必要
- サービス間のインターフェイス（フォーマット）を厳密に定義する必要がある（ADR-011参照）
- ローカル開発時に複数のサービスを起動する必要が出てくる

**リスク:**

- サービスの数が増えすぎると、リポジトリ全体の管理コストが上がる
- サービス間のバージョン整合性を取る運用が必要になる

## ADR-011

**サービス間のフォーマットは厳密に定義し、機械的な変換は決定論的に実装する**

- **日付**: 2026-04-08
- **ステータス**: 承認済
- **最終更新**: 2026-04-08
- **関連**: Doc/adr/ADR-004-ebnf-as-static-definition.yaml, Doc/adr/ADR-010-external-services-for-heavy-or-domain-specific-work.yaml

### 背景

ModelLogueと補助サービス（ADR-010）の間では、PlantUMLサブセット
ソース、状態遷移表CSV、テストケースCSV、JSONなど、さまざまな
フォーマットをやり取りする。

フォーマットが曖昧だと、便利なように見えて、結局「何が受容され
何が拒否されるのか」が分からなくなり、ユーザーもツール開発者も
困る。LLMで揺らぎを吸収する案もあるが、ハルシネーションの
リスクと、結果の説明責任の問題が残る。

特に、状態遷移図と状態遷移表は同じモデルの2つの表現であり、
両者の間の双方向変換は機械的に決定可能である。こうした
変換にLLMを使うのは、変換規則の説明可能性と再現性の点で
不適切。

**主な判断要因:**

- ユーザーが「何が通って何がエラーか」を予測可能であること
- サービス開発者がフォーマットを検証可能であること
- 再現性（同じ入力から常に同じ出力が得られる）
- 説明責任（変換結果の根拠を辿れる）
- オフラインでの動作（LLM呼び出しが不要）
- レイテンシと運用コストの抑制

### 決定

**要約:** サービス間でやり取りするフォーマットはすべて厳密に定義する。機械的に決定可能な変換は決定論的アルゴリズムで実装し、LLMには委ねない。

ModelLogueと補助サービスの間、および補助サービス同士の間で
やり取りされるフォーマットは、すべて事前に厳密に定義する
ことにした。フォーマット定義の方法は対象に応じて選ぶ：

- **PlantUMLサブセット**: EBNFで定義（既存）
- **CSV系（状態遷移表、テストケース等）**: 列定義表 + セル
  記述ルール表で定義。CSVはEBNFには馴染まないが、列の意味と
  取り得る値、エスケープ規則などを表として明文化する
- **JSON系**: JSON Schemaまたは TypeScript型定義で定義
- **その他**: 各形式に適した厳密な仕様で定義

機械的に決定可能な変換（例：状態遷移表CSV ↔ PlantUMLソース、
PlantUMLソース → 状態遷移マトリクス）は、決定論的アルゴリズムで
実装し、LLMに委ねない。

LLMは以下の用途に限定する：
- 自然言語での議論や説明（チャット）
- 仕様書のような自然言語からのモデル生成（フォーマット変換ではない）
- 曖昧な意図の解釈

変換結果が期待通りでない場合の対処は、フォーマット定義側を
更新するか、変換器側の不具合として修正する。LLMによる「何となく
動く」状態は許さない。

### 検討したが採用しなかった選択肢

- **フォーマットを緩く定義し、LLMで吸収する** — ユーザーが受容範囲を予測できず、再現性も説明責任も失われる。長期的には保守性が破綻する
- **LLMに変換させる（CSV→PlantUML等）** — 決定論的に書ける処理を確率的に処理するのは、ハルシネーション・レイテンシ・コスト・説明責任のすべての面で不利
- **フォーマット定義を後回しにして、まず動くものから作る** — 後から厳密化するのは、仕様不明な実装に依存したユーザーが出るので困難。最初から定義しておく方が安い

### 結果・影響

**メリット:**

- ユーザーが受容範囲を予測できる
- 変換結果が再現可能で説明可能
- LLM呼び出しが不要なのでオフラインでも動く
- レイテンシが小さく、運用コストも低い
- サービス開発時のテストが書きやすい
- フォーマット定義そのものがドキュメントになる

**受け入れる負債・制約:**

- フォーマット定義を最初に書く必要があり、初期コストが上がる
- フォーマット外の入力は受け付けないため、ユーザーが事前に整形する必要がある場合がある
- 決定論的アルゴリズムを書けない処理（自然言語からの推論等）には適用できない

**リスク:**

- フォーマットが厳密すぎると現実のユースケースに合わない場合が出てくる可能性
- フォーマットを変更する際の互換性管理が必要

## ADR-012

**モデル型プラグインアーキテクチャ（ModelTypeDefinition）**

- **日付**: 2026-04-22
- **ステータス**: 承認済
- **最終更新**: 2026-04-24
- **関連**: ADR-009 composite-states-minimal-subset (最小サブセット方針の先例), ADR-010 external-services-for-heavy-or-domain-specific-work (nswitch 枠組み), ADR-011 strict-formats-and-deterministic-conversion (決定論の方針), src/grammars/requirementDiagram.ebnf (本 ADR と対になる要求図サブセット定義), Doc/architecture.md §17 予定: モデル型フレームワークの実装詳細

### 背景

ModelLogue は当初「状態遷移図のレビュー支援」に特化して設計
されており、パーサ、ストア、解析タブ、AI プロンプト、nswitch
補助サービスまで、すべてが StateMachineModel を中心に作られて
いる。

レビュー対象として状態遷移図に匹敵する重要性のある第 2 のモデル
として「要求図」を追加したい。要求図は PlantUML に native 実装
がなく、`!procedure` マクロで class 図ベースにエミュレートする
コミュニティ慣習を ModelLogue の DSL として採用する方針
（Requirements_Specification.md §3.2 を新設予定）。

この第 2 型を場当たり的に追加すると、以下の問題が表面化する：

- `modelStore` が `model: StateMachineModel` を前提にしている
- 解析タブ（State×Event, State×State, Test cases）は状態遷移図
  固有で、要求図には意味をなさない
- EBNF・パーサ・差分計算・シリアライザの組が型ごとに必要
- Requirements タブを除く UI レイアウトはほぼ型依存
- 3 型目（クラス図、シーケンス図、等）が来た時点で、2 型目の
  場当たり対応を全て書き直すことになる

State machine への最適化が深いので、抽象の線引きを誤ると
かえって複雑性が増すリスクがある。

**主な判断要因:**

- 拡張性：将来、第 3 第 4 のモデル型が増える想定で、追加コスト を「新しいディレクトリを 1 つ作る」程度に抑えたい
- 既存挙動の保全：state machine の現在の振る舞いはリリース済み なので、refactor で挙動が変わってはならない
- ドキュメントとの整合：CLAUDE.md が「状態遷移図のレビュー」 と明記しており、これも汎用化に合わせて書き換える必要がある
- nswitch 等の補助サービス：型ごとに固有のサービスを想定する 必要があり、単純な analysis tab の置き換えでは収まらない

### 決定

**要約:** src/modelTypes/<type>/ 配下にモデル型ごとのパーサ・EBNF・解析タブ仕様・補助サービスクライアントを閉じ込め、ModelTypeDefinition インターフェースの registry で束ねる

以下の構造を採用することにした。

### ディレクトリ配置

    src/modelTypes/
      state-machine/
        parser.ts            -- PlantUML → StateMachineModel
        model.ts             -- StateMachineModel 型
        matrixGenerator.ts   -- 解析表の生成
        transitionTableSerializer.ts
        diff.ts              -- モデル差分
        grammar.ts           -- EBNF を ?raw import で束ねる
        definition.ts        -- ModelTypeDefinition の実体
        index.ts             -- export
      requirement/
        parser.ts            -- PlantUML (要求 DSL) → RequirementModel
        model.ts
        traceabilityMatrix.ts
        orphans.ts
        diff.ts
        grammar.ts
        definition.ts
        index.ts

### ModelTypeDefinition インターフェース（概略）

    interface ModelTypeDefinition<M> {
      id: string;                      // 'state-machine' | 'requirement'
      label: string;                   // UI 表示名
      description: string;             // 選択時のヒント
      grammar: string;                 // EBNF 本文（?raw import）
      parse: (source: string) => ParseResult<M>;
      analysisTabs: AnalysisTabSpec<M>[];   // Source/Requirements 以外の型固有タブ
      diff?: (before: M, after: M) => ModelDiff;
      defaultSeedSource?: string;      // 新規セッションの雛形
      externalServices?: ExternalServiceSpec[];  // 例: nswitch
    }

    const REGISTRY = [stateMachineDefinition, requirementDefinition];

### セッションとストア

- `SessionStore.modelTypeId: string` を新設。seed 時に固定、
  セッション中は変更不可
- `modelStore` は `model: unknown` に一般化し、型解決は
  ModelTypeDefinition 経由で行う。ただし型安全性は
  `useTypedModel<M>()` のような型パラメータ付きヘルパで担保
- 既存の `stateEventMatrix` / `stateStateMatrix` などの派生物
  は state-machine 固有なので、型ごとのサブストアに移動
  （例：`stateMachineAnalysisStore`）

### UI

- `AnalysisPanel` のタブ定義は ModelTypeDefinition.analysisTabs
  から組み立てる。Source / Requirements タブは共通
- ヘッダに **モデル型セレクタ**（seed 時に一度だけ選択可）を追加
- モデル型が異なるセッションを跨いで Open saved review した
  ときは、保存された型に自動追従

### 補助サービス（nswitch 類）

- ModelTypeDefinition.externalServices でヘルスチェック URL と
  client モジュールを登録
- state-machine の nswitch-api はこの枠組みで登録し直す
- 要求図の初版では externalServices は空配列（必要になった時点
  で「トレーサビリティギャップ分析」等を検討）

### 実装順（破壊的変更を避けて段階投入）

1. **refactor**: state machine コードを
   `src/modelTypes/state-machine/` に挙動不変で移設。
   既存 import path は re-export で維持
2. **framework + タブ動的化**: `ModelTypeDefinition` インター
   フェースと registry を導入。**同時に `AnalysisPanel` の
   タブ構成を `ModelTypeDefinition.analysisTabs` から動的構築
   するよう変更**（state-machine の S×E / S×S / Test cases は
   state-machine の analysisTabs として登録）。この時点で
   state-machine 単独で既存挙動が完全に再現されることを確認
3. **session**: `SessionStore.modelTypeId` とヘッダのモデル型
   セレクタを追加。選択肢は state-machine のみでも、
   ラウンドトリップ（Save & finish / Open saved review）で
   modelTypeId が維持されることを検証
4. **requirement parser**: `src/modelTypes/requirement/` の
   parser / model / preamble handler を実装、単体テスト
5. **requirement analysis**: Requirement list（SR-113）/
   Traceability（SR-111）/ Orphans（SR-112）タブを実装、
   `requirement` type の analysisTabs に登録すれば自動で
   AnalysisPanel に並ぶ
6. **end-to-end**: モデル型セレクタで requirement を選んで seed、
   AI で生成 → Apply → 解析タブ表示、を確認

各ステップで `tsc --noEmit` と `vitest` が緑に保てる粒度に
切る。ステップ 2 でタブ動的化を完了させておくことで、ステップ
5 で要求図タブを足す際に `AnalysisPanel.tsx` への変更が不要に
なる — これが ADR-012 の実用面での payoff。

### 検討したが採用しなかった選択肢

- **モデル型ごとに別リポジトリ／別アプリケーションにする** — レビュー UX（ソース編集、AI 対話、マーカー、セッション管理、
Save & finish など）が型に依存せず共通であり、別アプリに分離
すると共通部分を 2 重に維持する負荷の方が大きい。
- **共通コアだけ残し、型固有部分は AI プロンプトで吸収する** — パーサと差分計算は決定論的であるべき（ADR-011）。AI 頼みに
すると再現性が落ち、CI での検証にも向かない。
- **現在の構造を維持したまま要求図の path だけ if 文で分岐させる** — 分岐点が複数ストア・複数コンポーネントに散らばるので、3 型目
以降が加わったときの修正範囲が爆発する。ADR-009 で採った
「先に設計、後で段階的投入」の方針と矛盾する。
- **各モデル型で別々の SPA build を出す（ビルド時分岐）** — 型切り替えのために SPA を再読み込みさせる UX は n8n やマーカー
の state を失うので不利。1 つの SPA に registry を持たせる方が
軽い。

### 結果・影響

**メリット:**

- 新しいモデル型の追加コストが `src/modelTypes/<type>/` 配下の追加に集約される
- state-machine 固有コードが「その他の型に漏れない」ことが構造で担保される
- AI プロンプトや補助サービスの切り替えも同じ registry 経由で扱える
- テスト・build・CI は現状の粒度で問題なく回る（単独パッケージ数増えるだけ）

**受け入れる負債・制約:**

- refactor のため、state-machine 関連コードの import path が一括で変わる
- `modelStore` の型が弱くなり、型安全性をヘルパ関数で補う必要がある
- `CLAUDE.md` の「状態遷移図のレビュー」という記述を汎用化する書き換えが必要
- 1 つの SPA で複数型を扱うため、バンドルサイズがモデル型数に応じて線形に増える（将来的に遅延ロードで対応可能）

**リスク:**

- 抽象の設計を 2 型だけで切るため、3 型目で穴が見つかって interface を拡張することになる可能性
- seed 時に型を間違えた場合の救済 UX が未設計（別セッションを作り直すのが現状最善）
- nswitch 類の補助サービス URL が型ごとに増える運用負荷（docker-compose の管理が複雑化）

## ADR-013

**要求図のレビューとダウンストリームトレーサビリティは別フェーズとして扱う**

- **日付**: 2026-04-22
- **ステータス**: 承認済
- **最終更新**: 2026-04-22
- **関連**: ADR-008 scope-boundary-with-surrounding-workflow (同種のスコープ境界決定), ADR-012 model-type-plugin-architecture (要求図追加の全体方針), UR-014 Review requirement diagram, src/grammars/requirementDiagram.ebnf (satisfy / verify / trace は構文としては受容)

### 背景

要求図サポート（v7.5、UR-014、ADR-012）の設計を進める中で、
SysML 要求図が定義する関係種別を整理すると、大きく 2 群に
分かれることが明らかになった：

1. 要求 ↔ 要求の関係
   - $contain: 階層・包含（パッケージまたは大要求の内訳）
   - $derive:  派生（上位要求から下位要求への根拠付き分解）
   - $refine:  詳細化（同じ意図のより具体化された別表現）
   - $copy:    コピー関係

2. 要求 ↔ 外部アーティファクト（設計・テスト）の関係
   - $satisfy: 設計要素が要求を充足する
   - $verify:  テストケースが要求を検証する
   - $trace:   汎用トレーサビリティ

要求図レビューの目的（要求リストと要求どうしの関係の質を
上げる）は 1 群で完結する。2 群を同じレビュー UX に含めよう
とすると、以下が追加で必要になる：

- 設計要素・テストケースを ModelLogue 内で参照できるようにする
  外部アーティファクト registry（現状なし）
- 要求 × 外部アーティファクトのクロスマトリクス UI
- 複数フェーズ（要求確定 → 設計 → テスト）をまたぐセッション
  設計

これは「表に列を増やす」話ではなく、レビューの目的と UI 構造が
質的に別物になる領域である。

**主な判断要因:**

- 要求図レビューの目的（要求の質向上）とダウンストリーム トレーサビリティの目的（実装・検証の網羅性確認）は本質的に別
- v7.5 のスコープ肥大を避ける（既にモデル型プラグイン構造 ADR-012 という大きな構造変更を含む）
- 外部アーティファクトの表現方法は ModelLogue のセッション モデル全体の再検討を要するので、軽く足せない

### 決定

**要約:** v7.5 の要求図サポートは要求 ↔ 要求の関係（derive / contain / refine / copy）に限定し、要求 ↔ 外部（satisfy / verify / trace）は別フェーズの別機能として後日設計する

v7.5 の要求図レビューは「要求リストと要求どうしの関係の質を
上げる」ことに目的を絞る。具体的には：

- 要求リスト表（SR-113）の列は derive（`derives_from`）と
  contain（`contained_in`）の 2 種のみを持つ
- Traceability タブ（SR-111）では refine / copy も含めた
  要求間関係を kind ラベル付きで表示する
- Orphans タブ（SR-112）は要求間関係の incoming / outgoing の
  有無で孤立を判定する

parser（SR-110）と DSL（`src/grammars/requirementDiagram.ebnf`）
は satisfy / verify / trace を構文として受け入れる。理由は
2 つ：
- PlantUML Server にそのまま描画されるので、ユーザーが書いた
  ものが画面から消えるという不整合を避ける
- 将来のダウンストリームトレーサビリティ機能追加時に後方
  互換性を取りやすい

ただし、v7.5 の解析タブは satisfy / verify / trace を**特別
扱いしない**。Traceability タブに「kind = satisfy」として
並ぶ程度で、専用 UI は提供しない。

将来のダウンストリームトレーサビリティ機能（仮称：
Traceability Review）は、実需が出てきた時点で以下のどれかの形で
設計する：
- 別モデル型として登録（ModelTypeDefinition 再利用）
- 同じ要求図モデル型に「レビューフェーズ」の概念を加える
- 独立したアプリケーション・サービスとして切り出す

### 検討したが採用しなかった選択肢

- **v7.5 で satisfy / verify / trace も要求リスト表の列にする** — 外部アーティファクト（設計要素・テストケース）の識別子を
どう持つかが決まっていない。パスやファイル名の文字列で持つ
のか、別の registry で解決するのか、ModelLogue が設計文書や
テストフレームワークとどう連携するか、という別の設計が
必要。列だけ足しても「未接続の文字列を溜める箱」にしか
ならず、レビューの質向上に寄与しない。
- **要求図全体を要求 ↔ 外部も含めて v7.5 で一気に扱う** — v7.5 はモデル型プラグイン構造（ADR-012）という大きな構造
変更を既に含む。外部アーティファクト管理まで乗せると
リリース粒度が大きくなりすぎて、問題発生時の切り分けが
困難になる。小さく実装・小さく検証の方針と矛盾する。
- **satisfy / verify / trace を完全にサポートしない** — ユーザーから「将来、テストまでのトレーサビリティを取りたい」
との明示的な意図が示されている。完全撤廃は要求と矛盾する。

### 結果・影響

**メリット:**

- v7.5 のスコープが要求 ↔ 要求に絞られて小さく、検証しやすい
- 要求図レビューの目的が明確になる（要求の質を上げる）
- DSL パーサが satisfy / verify / trace を受容するので、将来機能追加時の後方互換を取りやすい
- 外部アーティファクト registry という大きな設計を、実需が明確になってから行える

**受け入れる負債・制約:**

- ユーザーが DSL に書いた satisfy / verify / trace は v7.5 では目立った UI を持たない（Traceability タブに一行として並ぶだけ）
- ダウンストリームトレーサビリティ機能の設計負荷が将来に繰り越される

**リスク:**

- ユーザーが Requirements タブや AI 対話で satisfy / verify / trace を書いてしまい、レビューで活用できないことに後から気づく可能性 — SR-110 の入力形式仕様とタブ上の案内で明示的に「v7.5 のレビュー対象は要求 ↔ 要求のみ」と伝える
- 将来の設計時に「別モデル型」「レビューフェーズ」「別アプリ」のどれを選ぶかは、外部アーティファクトの性質を見てから再判断する必要がある

## ADR-014

**レビュー過程の削除は soft-delete + reason 必須でエビデンスとして残す**

- **日付**: 2026-04-22
- **ステータス**: 承認済
- **最終更新**: 2026-04-22
- **関連**: ADR-001 frontend-is-pure-ui (Dialogue as Asset / Volatile Canvas の初出), ADR-012 model-type-plugin-architecture (要求図追加の全体方針), ADR-013 requirement-review-scope-boundary (v7.5 のスコープ), SR-110 / SR-113 / SR-114 (v7.5 で本原則を実装する SR 群), src/grammars/requirementDiagram.ebnf ($hide / $deleted / $note マクロの文法)

### 背景

要求図レビュー（UR-014、v7.5）の設計を詰める過程で、レビュー
結論として「この要求は削除する」と決めるケースが頻繁に発生する
ことが明らかになった。単に要求リストから行を消すと：

- 後から「なぜその要求を消したのか」を説明できない
- チャットログには対話の痕跡があるが、粒度が粗い（数百行の
  dialogue から該当箇所を探し出すコストが高い）
- 監査・顧客説明・リグレッション防止のために「削除した要求＋
  削除理由」という明示的な記録が有用

ModelLogue の核心原則は ADR-001 の "Volatile Canvas" と
"Dialogue as Asset" であり、**対話と決定の痕跡を資産として
扱う**姿勢を持つ。削除の扱いもその延長上に位置づけるべき。

同じ論点は将来的には要求図だけでなく他のモデル型（状態遷移図
の state / transition 削除、クラス図の class 削除、etc.）に
も波及しうる。したがって個別機能の実装詳細ではなく、**レビュー
における削除の一般原則**として記録する価値がある。

**主な判断要因:**

- Dialogue as Asset 原則との一貫性
- 監査・顧客説明・リグレッション防止の実務ニーズ
- チャットログだけでは削除の根拠追跡が粗すぎる
- 他のモデル型にも同種の要求が出る可能性（クロスカット設計）

### 決定

**要約:** レビュー過程で削除と判断された要素は hard-delete せず、deleted フラグ + reason（備考）を併記して保持する。エクスポート artifact にも含めて将来参照可能にする。表現形式は PlantUML コメント（`' @modellogue ...`）にして、source を直接 PlantUML に送っても妥当なまま保つ

レビューの成果物としてのモデル（要求リスト、状態遷移モデル、
etc.）において、「削除」と決まった要素は以下の方針で扱う：

1. **Soft-delete**: 要素を model から物理削除しない。削除
   フラグ（`deleted: boolean`）を true に設定するのみ
2. **Reason 必須**: `deleted=true` にする際は、削除理由を
   `note`（備考）フィールドに記録することを必須化する
3. **全ての永続形式で round-trip**: DSL（PlantUML サブセット）、
   CSV、Save & finish の JSON のいずれでも deleted + reason は
   保存される
4. **可視化**: リストビューでは打ち消し線＋薄灰で常時表示
   （見える = エビデンス）、図（PlantUML）では該当行が
   コメントアウトされているので描画されない
5. **復元可能**: deleted フラグを false に戻せば元に戻る（
   削除は取り消し可能な状態遷移）

### 表現形式の制約（2026-04-23 追補）

review-state（hide / deleted / note）の表現は **PlantUML コメント**
に限る。理由：

- DSL は PlantUML のサブセットでなくてはならない（本ツールを
  通さず、source を直接 PlantUML に送っても有効）
- ModelLogue が独自に `$hide` / `$deleted` / `$note` のような
  macros を導入すると「勝手に作った DSL」になり、上の原則に違反
- コメント（`'` で始まる行）は PlantUML が完全に無視するので、
  任意のメタデータを埋め込んでも source の妥当性は崩れない

したがって以下の形式を採る：

    ' @modellogue hide "R1"
    ' @modellogue deleted "R2" "out of scope"
    ' @modellogue note "R3" "needs review"

削除ブロックは marker に加えて、対象の宣言行そのものを
コメントアウトし、触れる関係行には `deleted-side` タグを付ける：

    ' @modellogue deleted "R2" "out of scope"
    ' $fReq("R2", "old requirement")
    ' $derive("R1", "R2") ' @modellogue deleted-side "R2"

これで source を PlantUML に直接送った場合も R2 は描画されない
（全てコメント）。ModelLogue を通すと parser が marker を読み取り、
R2 を `deleted=true` として model に載せ、リストタブで打ち消し線
表示 + note 欄に理由を表示する。

### 非表示との違い（2026-04-23 ユーザー確認）

- **Delete**: source 自体でコメントアウト済み。どこに送っても
  現れない。ブロック全体がエビデンスとして残る
- **Hide**: source では宣言を残す（コメントアウトしない）。
  source を直接 PlantUML に送ると描画される。ModelLogue を
  通したときだけ、renderer が送信前に該当行をコメントアウト
  してフィルタする（SR-114）

note フィールドは削除理由専用ではなく、**任意の要素に付けられ
る自由メモ欄**として設計する。削除時には非空必須という制約が
追加で課されるだけで、通常運用では「曖昧、要確認」「次回
再検討」のような作業メモとして使える。

v7.5 ではまず要求図（Requirement）にこの原則を適用する（
SR-113 のデータモデル、SR-110 の DSL 解釈、SR-114 の renderer
フィルタ）。状態遷移図への波及は必要が出てきた時点で別 ADR
として検討する（現時点では chat ログで十分運用できている）。

### 検討したが採用しなかった選択肢

- **hard delete + チャットログで経緯を残す** — チャットログは会話単位の記録で、数百行の対話から「なぜ R5
を消したのか」を探すのは実務上コストが高い。要素自体に
reason を付ける方が検索性・引用性の両面で勝る。
- **hard delete + 別ファイル（deleted.log 的なもの）に移動** — Save & finish の JSON、CSV、DSL 全てで独立した削除ログを
round-trip させる必要が出て、単一の artifact で完結しない。
レビュー成果の受け渡し時に「本体と削除ログの両方を揃える」
という運用ミスの余地が増える。
- **削除は全て hidden（非表示）で表現、hard delete は一切行わない** — 「削除したい」と「今は見たくない」は意思の強さが違う。
両者を 1 つのフラグで表現すると、後から artifact を読み
返した時に区別できず、レビューの結論として何を決めたのか
が曖昧になる。
- **Note 欄を削除理由専用に限定する** — 「曖昧、要確認」のような作業メモも実務で頻出する。用途を
削除理由に限定すると、別途作業メモ用のフィールドを足す
ことになり、モデルが不必要に肥大する。1 つの自由記述欄を
削除時に制約付きで使う方が経済的。

### 結果・影響

**メリット:**

- レビュー成果物 1 つで「何を決めたか、なぜそうしたか」が自己完結する
- Dialogue as Asset 原則がモデル要素レベルまで一貫する
- 監査・顧客説明・将来のリグレッション調査に耐えうるエビデンス
- 削除が取り消し可能なので、レビュー中に気軽に「一旦削除」扱いにできる
- note が自由メモ欄としても機能するので、削除に至らない曖昧状態の記録にも使える

**受け入れる負債・制約:**

- data model に hidden / deleted / note の 3 フィールドが追加され、CSV / DSL / JSON のスキーマが少し膨らむ
- deleted 行が累積するとリストビューの視認性が落ちる可能性（将来的に「削除行を折りたたむ」UI が必要になるかも）
- AI プロンプトに「削除時は $deleted(id, reason) を使い reason 必須」というルールを明記する必要があり、プロンプト肥大の一因になる

**リスク:**

- ユーザーが「単に要らない」ものまで deleted で残してしまい、リストが雑然とする
- hidden と deleted の使い分けが曖昧になるケースで迷う（運用ガイドが必要）
- 将来、状態遷移図側に同じ原則を展開するかどうかの判断が残る — 本 ADR は要求図限定の適用から始める
